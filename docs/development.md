# Разработка YummyWatch

[← Вернуться к README](../README.md)

> Work in progress. Основной клиент — приложение Tauri 2 для macOS и Windows. Веб-стенд сохранён для разработки.

## Нативное приложение

`npm run dev` запускает Tauri и Vite, `npm run build` собирает установочные пакеты текущей ОС. Для отдельного веб-стенда — `npm run dev:web` / `npm run build:web`. В установленном приложении нет Node.js, Vite, локального HTTP-сервера, TCP listener или отдельного серверного процесса.

- `src-tauri/src/lib.rs` — команды `desktop_info`, `yummy_request`, `resolve_candidates`, `inspect_stream_qualities` и асинхронный протокол `yumiwatch-media`.
- `src-tauri/src/providers.rs`, `alloha.rs`, `skips.rs` — Rust-реализация Kodik, Aksor, CVH и Alloha, разбор меток пропуска, сессии ретрансляции. Скрипты источников разбираются как данные и не исполняются.
- `src-tauri/src/backend.rs`, `media.rs` — состояние и кэш resolver, обработка внутренних медиа-запросов Alloha и CVH.
- `src/lib/desktop.ts` — IPC, отмена ожидания результатов при смене страницы, открытие внешних HTTPS-ссылок в браузере. `yummy_request` разрешает только фиксированные API-хосты `api.yani.tv`, `old.yummyani.me`, `ru.yummyani.me` и заголовки API; секреты не пишутся в логи.
- `src/components/WindowChrome.tsx`, `src/desktop.css`, конфиги `tauri.macos.conf.json` и `tauri.windows.conf.json` — кнопки поверх интерфейса, область перетаскивания и общий отступ 44 px. Полный экран переключается через Tauri и убирает отступ. На macOS отступ контента не создаёт фиксированной полосы над прокруткой; логотип поднят на 10 px независимо от меню. Прозрачный WebView и `windowEffects: sidebar` включают системный vibrancy, CSS задаёт полупрозрачные тёмные подложки. Видео и контрастная тема сохраняют непрозрачный фон.

Обработка потоков реализована только на Rust. Десктопный клиент вызывает её через IPC; сохранённый в старых настройках адрес HTTP-resolver игнорируется и удаляется при следующем сохранении настроек. В Vite нет middleware для потоков. Браузерный стенд поддерживает прямой CVH для предпросмотра, остальные источники проверяются в Tauri или через Rust `media_probe`. Service worker и предложение PWA-установки в Tauri отключены: интерфейс уже находится в пакете приложения.

Alloha возвращает только зарегистрированные адреса вида `alloha/<session>/<resource>`. Клиент переводит их в `yumiwatch-media://localhost/...` (на Windows WebView2 использует перехваченный `http://yumiwatch-media.localhost/...`, без TCP-соединения). Внутренний обработчик проверяет origin, ID сессии и ресурса, допускает только CDN `*.userplay.live` и пути выбранной серии. Заголовки сессии остаются в Rust. Ключи, init-сегменты, варианты, субтитры и медиасегменты проходят через тот же протокол; Range сохраняется. Ответы ограничены 512 КБ для плейлистов и 32 МБ для сегмента, одновременно загружаются не больше четырёх ресурсов. На платформах с WebView-видеовыводом Shaka загружает такие HLS-потоки через MSE, поскольку AVFoundation не открывает пользовательскую схему.

Кэш resolver ограничен 64 результатами на 30 секунд, сессии Alloha — восемью, с истечением через 3 минуты бездействия или 45 минут жизни. Файлы сессий и токенов потоков не создаются. Отмена IPC на стороне интерфейса игнорирует поздний ответ; исходящий запрос Rust завершается по своему таймауту.

Списки, избранное, история просмотра и подписки на озвучки собраны в `/profile`. Гостевой профиль открывается без входа. Старые адреса `/library` преобразуются в соответствующие вкладки профиля через `history.replaceState`, сохраняя состояние истории переходов. История и подписки видны только в собственном профиле.

`npm run test:rust` проверяет все четыре провайдера на подготовленных ответах, nonce Alloha, изоляцию озвучек/субтитров, метки пропуска, переписывание HLS и проверки протокола. Тесты не открывают сетевые порты.

Для проверки живых источников без локального HTTP-сервера:

```sh
cargo test --manifest-path src-tauri/Cargo.toml live_provider_transport -- --ignored --nocapture
```

Проверка получает публичные серии Yummy, отдельно запускает Rust-resolver для Aksor, Kodik, Alloha и CVH, проходит внутренние HLS-плейлисты до первого медиасегмента и проверяет ключи/init-ресурсы. Нужен доступ к источникам, поэтому она исключена из обычного офлайн-прогона. Секретные заголовки и ссылки CDN в вывод не попадают.

Kodik использует base64 без обязательного `=`; декодер повторяет поведение браузерного `atob`. Для ответов источников в reqwest включена распаковка gzip. CVH использует `hlsUrl` из ответа API и регистрирует все качества в одном внутреннем ресурсе. WebView не обращается к CDN напрямую: медиазаголовки браузеров приводят к HTTP 400 на OK CDN. Rust отправляет только собственные заголовки и переписывает варианты, ключи и сегменты HLS в `media/<session>/<resource>`. Если HLS отсутствует, остаётся ограниченная MP4-ретрансляция с Range до 8 МБ. Разрешены только HTTPS CDN `*.okcdn.ru` и `*.mycdn.me`, ресурсы регистрируются из доверенных ответов API и плейлистов. Обычный MP4 без прокси не требует `crossorigin`. При воспроизведении в WebView внутренний HLS-протокол использует MSE без отката на AVFoundation; MIME передаётся Shaka явно. Ошибки Rust IPC преобразуются в `Error`, чтобы интерфейс показывал причину вместо бесконечной загрузки. Для Alloha одна дорожка `(Undetermined) 1` или `(Russian) 1` принимается только при подтверждении выбранной студии в `fileList.active.translation`; несовпадающая студия и субтитры через этот путь не подменяются.

Сквозная проверка реального Rust-бэкенда и декодирования в WebKit:

```sh
npx playwright install webkit
npm run check:desktop-player
MEDIA_BROWSER=chrome npm run check:desktop-player
```

По умолчанию проверяется «Чёрный клевер 2», SHIZA Project, первая серия: CVH, Kodik и Alloha. Параметры — `ANIME_ID`, `PLAYER_VOICE`, `PLAYER_EPISODE`, необязательный фильтр `PLAYER_FAMILY`. `RESOLVE_ALL=1` передаёт все источники вместе и проверяет переход resolver к рабочему провайдеру. Проверка ждёт декодированных кадров и двух секунд воспроизведения, затем перематывает на 60 секунд и ждёт продолжения. `media_probe` — тестовый пример Rust, общающийся только через stdin/stdout. Playwright заменяет обработчик протокола WebView перехватом запросов; веб-сервер и TCP listener для проверки не запускаются. Системное окно Tauri эта проверка не открывает.

## Yummy API

Используется [документация Yummy](https://api.yani.tv/swagger):

| Назначение                        | Запрос                                                                                    |
| --------------------------------- | ----------------------------------------------------------------------------------------- |
| Каталог и поиск                   | `GET /anime`                                                                              |
| Подробности                       | `GET /anime/{id}`                                                                         |
| Распределение оценок аниме        | `GET /anime/{id}/rates`                                                                   |
| Личная оценка аниме               | `PUT/DELETE /anime/{id}/rate`                                                             |
| Серии и озвучки                   | `GET /anime/{id}/videos`                                                                  |
| Расписание                        | `GET /anime/schedule`                                                                     |
| Вход, профиль и обновление сессии | `POST /profile/login`, `GET /profile`, `GET /profile/token`                               |
| Личные списки и избранное         | `GET /users/{id}/lists`, `PUT/DELETE /anime/{id}/list`, `PUT/DELETE /anime/{id}/list/fav` |
| Подписки на озвучки               | `GET /users/{id}/lists/subs`                                                              |
| История и сохранение просмотра    | `GET /video/watch-history`, `PUT /video/{id}`                                             |
| Все жанры и теги                  | `GET /anime/genres`                                                                       |
| Обсуждения и ответы               | `GET/POST /comments/anime/{id}`, `GET /comments/{id}/children`                            |
| Оценки комментариев               | `PUT/DELETE /comments/{id}/vote`                                                          |

В веб-стенде запросы отправляются напрямую на `https://api.yani.tv`; в Tauri — через нативную IPC-команду с тем же API-контрактом с `Lang: ru`. При сетевой ошибке, тайм-ауте, HTTP 408/5xx или некорректном ответе клиент перебирает резервные API: `https://old.yummyani.me/api`, затем `https://ru.yummyani.me/api`. На каждую попытку отводится 5 секунд, рабочий адрес запоминается в памяти. Пока выбран резерв, клиент раз в минуту проверяет основной API отдельным GET `/anime?limit=1` без токена аккаунта и автоматически возвращается к нему после валидного ответа. Запоздалые ответы зеркал не отменяют восстановление; проверки приостанавливаются при скрытом окне или отсутствии сети. После отказа последнего адреса перебор возвращается к основному. HTTP 4xx (кроме 408), ошибки авторизации и капча не запускают переключение; 401 очищает только соответствующую сессию. Автоматически повторяются только GET/PUT/DELETE; POST/PATCH не переотправляются после неоднозначного сбоя, а следующая явная попытка использует резерв. Кэш и дедупликация запросов общие для всех зеркал. Нативный транспорт проверяет точный HTTPS-origin и префикс `/api/` у зеркал, запрещает редиректы; токены не отправляются произвольным доменам. На момент проверки 14 ноября 2026 года эти публичные маршруты отвечали без токена, а CORS разрешал GitHub Pages. По документации необходимо зарегистрировать приложение на <https://yummyani.me/dev/applications> и передавать его **публичный** токен в `X-Application`. API предназначен для личного использования; для коммерческого применения авторы API просят связаться с ними.

Токен приложения можно указать в дополнительных настройках локального клиента или в `.env.local` как `VITE_YUMMY_APPLICATION_TOKEN`. Токен из переменной сборки публично доступен в JS — это должно быть именно значение для публичного приложения. Пароли, пользовательские токены аккаунта и секретные ключи в настройки приложения или переменные сборки добавлять нельзя.

## Кэш данных и изображений

`src/lib/cache-store.ts` держит данные в RAM и сохраняет снимок в IndexedDB. До первого рендера приложение восстанавливает метаданные и изображения в память. Старые 35 записей localStorage мигрируют автоматически; fallback для окружений без IndexedDB сохраняется. Лимиты LRU: 512 записей и 16 МиБ для данных, 512 изображений и 128 МиБ для изображений.

Каталог, поиск, расписание, описания, озвучки, серии и комментарии используют stale-while-revalidate: синхронный `peek` сразу заполняет экран, а свежий ответ подменяет данные на месте. Одновременные одинаковые запросы объединяются; уход одного экрана не отменяет обновление для другого. При возврате обновляются и ранее загруженные страницы каталога. Изменение списка серий не сбрасывает выбранную серию, озвучку, позицию или декодер видео.

`CachedImage` использует сохранённый Blob URL и фоновое обновление. Одинаковые байты не меняют `src`; изменившаяся картинка заменяется на экране. Для IndexedDB сохраняются ArrayBuffer и MIME, что работает и в WebKit с ограничением на Blob-записи. Изображения запрашиваются только при приближении к видимой области (IntersectionObserver, запас 160 px); скрытые сохранённые экраны и карточки за пределами горизонтальной полки не заполняют очередь. Метаданные больше не запускают предзагрузку всех размеров. Обычные карточки используют medium, крупные постеры — big; на Retina выбирается следующий размер, чтобы сохранить резкость. Одновременно идут до шести запросов; фоновая проверка уже сохранённых картинок занимает максимум два слота. Очередь FIFO, одинаковые запросы объединяются, ненужные задания отменяются до старта. Декодирование асинхронное; уже видимая картинка не проходит вторую нативную lazy-проверку. Команда `fetch_image` обходит CORS WebView через существующий Rust-клиент и следует только проверенным CDN Yummy/Kodik, без listener или HTTP-сервера. Видео и временные адреса медиасессий в этот кэш не входят.

Сетевая ошибка оставляет сохранённую версию. Явные 401/403/404 удаляют запись. Пользовательские результаты отделены ключом аккаунта и сессии; исходный токен не сохраняется в снимке. Нормальное фоновое обновление не добавляет и не убирает баннер, сдвигающий контент.

`npm run check:cache` проверяет production-интерфейс, Rust-загрузку изображений, замену метаданных после задержанного ответа и восстановление описания, озвучек, серий, постера и полноразмерного скриншота после перезапуска без сети в WebKit и Chrome. Системные команды окна в стенде заменены тестовыми.

## Аккаунты и синхронизация

Вход доступен по значку аккаунта в шапке и в настройках. Пароль отправляется непосредственно на `https://api.yani.tv/profile/login`, `need_json: true`; он не сохраняется в хранилище, кэш, репозиторий или сборку. Пользовательский токен передаётся в `Authorization: Yummy …`, как в клиенте исходного сайта и security scheme Swagger. Это другой токен, чем публичный `X-Application`.

По умолчанию токен с минимальным профилем хранится в `sessionStorage`; при явном выборе «Оставаться в аккаунте» — в `localStorage`. При восстановлении сессия проверяется через `/profile`; токен старше двух дней обновляется через `/profile/token`. При HTTP 401 текущая сессия очищается. При выходе данные аккаунта удаляются из памяти; гостевая коллекция сохраняется. Аккаунт не получает гостевые данные автоматически.

Авторизованные запросы выполняются без HTTP-кэша и не попадают в публичный офлайн-кэш или service worker. Это относится и к каталогу с исключением личных списков. Сырые ответы коллекции хранятся в памяти. Списки серий с прогрессом и каталоги с личными фильтрами сохраняются в изолированном кэше аккаунта и сессии; они не доступны гостю и другим аккаунтам. Для «Продолжить просмотр» отдельно сохраняются до 100 нормализованных записей по ID аккаунта: ID/название аниме, постер, серия, videoId, позиция, длительность и дата. Токены и адреса потоков сюда не попадают. Неподтверждённые локальные записи не затираются старой историей сервера; успешная запись подтверждает кэш, а новая серверная история удаляет уже подтверждённые отсутствующие записи. Гостевой кэш отделён. Запоздавшие ответы старой сессии игнорируются; записи просмотров сериализованы, чтобы медленный запрос старой серии не заменил новую. Для изменения коллекции аккаунта и загрузки её свежих списков нужен интернет; сохранённое продолжение просмотра доступно без сети. При возвращении в приложение коллекция обновляется. Все пять статусов загружаются одним запросом `/users/{id}/lists`; избранное выделяется по `user.list.is_fav` и остаётся независимым. Изменение статуса подтверждается сервером перед обновлением интерфейса. Подписки на озвучки доступны для чтения отдельным запросом. Гостевые статусы сохраняются локально и не смешиваются с аккаунтом.

### Проверка входа через сайт

На 14 ноября 2026 года поддерживаемого внешнего OAuth/OIDC-потока для входа в YummyWatch через существующую сессию YummyAnime не найдено. Проверены актуальный [Swagger](https://api.yani.tv/swagger), публичный [клиент сайта](https://ru.yummyani.me/) и стандартные метаданные OAuth/OIDC на доменах `ru.yummyani.me` и `api.yani.tv` (HTTP 404).

- Swagger описывает получение пользовательского токена через `POST /profile/login` и обновление через `GET /profile/token`. `X-Application` идентифицирует приложение и не является пользовательской авторизацией.
- В клиенте сайта есть входы через Discord, VK, Shikimori и Telegram. Их redirect URI ведут на YummyAnime; механизма передачи токена в сторонний callback в проверенном клиенте не обнаружено. Настройки приложения в `/apps` содержат имя и описание, без настройки redirect URI.
- Passkey-маршруты присутствуют, но ключ сайта привязан к его RP ID. Использование ключа с GitHub Pages потребовало бы поддержки связанного origin со стороны YummyAnime — это следует из [WebAuthn](https://www.w3.org/TR/webauthn-3/#sctn-rp-id). Проверенный `/.well-known/webauthn` на `ru.yummyani.me` также отвечает 404.

Поэтому кнопка входа через сайт не добавлена: открытие сайта само по себе не авторизует YummyWatch. Для такого сценария нужен предоставленный Yummy поток авторизации для стороннего приложения с проверяемым callback. Существующий вход через API продолжает работать.

Если Yummy отвечает HTTP 420 или `error_code: 5`, экран входа показывает HCaptcha с site key из документации Yummy. Скрипт загружается только при необходимости. Капчу проходит пользователь, затем повторяет вход; доступность виджета и разрешённые домены определяются Yummy / HCaptcha. Социальный вход не реализован.

Страница просмотра всегда использует нативный плеер; iframe на ней не создаётся. Оригинальные плееры доступны отдельными ссылками по озвучкам на странице аниме. Компонент `Player` сохраняет совместимость с прежним режимом iframe для изолированного использования: сообщения принимаются только от текущего iframe и его origin. На основном маршруте `Detail` принудительно выбирает `modeOverride="universal"` и `presentation="immersive"`, независимо от прежних настроек устройства. Открытие страницы само по себе не записывается как просмотр — запись начинается с события воспроизведения/прогресса. Без сети видео недоступно. Офлайн-страницы появляются после первого успешного посещения; браузер может очистить локальные данные.

## Локальный стенд

Скрипт деплоя и шаблон Pages workflow удалены. Текущий клиент используется для разработки и проверки будущего мобильного приложения.

Публичный сайт снят с публикации, ветка `gh-pages` удалена.

```sh
npm ci
npm run dev:web -- --port 4179
```

Vite обслуживает только интерфейс на `http://127.0.0.1:4179/`. `npm run dev` открывает Tauri с Rust-backend; `npm run dev:web -- --port 4179` запускает браузерный предпросмотр. `npm run build:web` и `npm run preview -- --port 4179` позволяют проверить собранный интерфейс в браузере. Для сборки нативного приложения используется `npm run build`.

## Структура

Снимки не меняют высоту или координаты группы из-за прокрутки; меню остаётся смонтированным и уезжает transform, а не исчезает с пересчётом геометрии.

При выбранном сохранении входа используется файл `account/session-v1.json` в `app_data_dir()` с прежним идентификатором приложения. Каталог на Unix создаётся с правами 0700, файл — 0600; на Windows используется папка данных текущего пользователя. Запись идёт через отдельный временный файл, sync_all и атомарное переименование. API и медиа обрабатываются настоящим Rust-бэкендом через stdio; HTTP listener не создаётся. Скрипт снимает каталог, поиск, описание, фильтры, серии, декодируемое видео и гостевую коллекцию. Сохранены графитовые поверхности и коралловый акцент приложения.

## Универсальный плеер и Rust-backend

### Нативное видео на macOS

«Наш плеер» выводит видео через libmpv в AppKit. WebView отвечает за кнопки, меню и панели поверх видео. libmpv использует VideoToolbox для H.264/HEVC и AudioToolbox для AAC, MP3, AC-3 и E-AC-3. Программный откат выключен. Для Alloha и CVH протокол `yumiwatch://media/` в комплектном FFmpeg вызывает Rust-бэкенд внутри процесса и читает зарегистрированные плейлисты, сегменты и диапазоны байтов. Для этого не открывается локальный порт.

Для `npm run dev` и `npm run build` нужны Xcode Command Line Tools, `pkg-config` и Python с пакетами `meson`, `ninja`, `Jinja2`. При первом запуске скрипт `packaging/macos/build-libmpv.sh` скачивает исходники с фиксированными контрольными суммами. Сборка кладёт одну `libmpv.2.dylib` в `Contents/Frameworks` и включает рядом лицензии и рецепт сборки. Для отладки можно задать `YUMIWATCH_LIBMPV` абсолютным путём к установленной совместимой libmpv.

### Нативное видео на Windows и Linux

На Windows libmpv выводит видео через D3D11 в дочернее окно под WebView2. На Linux libmpv рисует через OpenGL в `GtkGLArea` под WebKitGTK. Область плеера в WebView прозрачная, кнопки и меню остаются поверх видео. Потоки Alloha и CVH идут через Rust-бэкенд по адресу `127.0.0.1` со случайным ключом сеанса. Ответы CVH передаются в libmpv непрерывно, сохраняя ограничения на размер запросов к CDN и поддержку перемотки.

Для сборки Linux на Ubuntu 24.04 установи `libmpv-dev`. В CI компактная Windows DLL собирается из закреплённых исходников по рецепту `packaging/windows/build-libmpv.sh`. В Windows-сборку входят демультиплексоры MP4, HLS и DASH, декодеры для потоков приложения, рендерер D3D11, аппаратное декодирование D3D11VA, WASAPI и поддержка субтитров. Для локальной сборки Windows можно подготовить компактный комплект в `src-tauri/native-libs/windows/` тем же скриптом на Ubuntu 24.04 с MinGW. Скрипт подготовки проверяет его контрольные суммы. Если совместимого локального комплекта нет, используется официальный LGPL-архив libmpv с проверкой SHA-256.

### Поток, прогресс и пропуск заставок

Наш плеер связывает сеанс с фактическим `videoId` из ответа resolver, а не с первым вариантом серии в списке озвучек. Внутри плеера показаны провайдер, домен видеосервера, качество, формат и позиция. Статус сохранения расположен в углу и скрывается вместе с управлением. Время фактического просмотра доступно в событиях сеанса. При восстановлении предпочтение получает источник из истории; если он недоступен и выбран другой, прогресс записывается уже для нового источника.

После начала воспроизведения позиция сохраняется каждые 10 секунд, при паузе, завершении перемотки, смене серии/озвучки/режима и выходе со страницы. В аккаунте выполняется `PUT /video/{videoId}` с `{ time, duration, date }`: `time` — позиция в серии в секундах, включая результат перемотки или пропуска. Так история на исходном сайте и PWA использует один идентификатор потока. Записи сериализуются на аккаунт и аниме; старый сеанс не пишет в новый аккаунт. Без входа сохраняется гостевая история устройства. Ошибка API показывается явно, позицию можно отправить повторно. На сервер потоков пользовательский токен не передаётся.

`<Player onPlayback={event => …}/>` и событие окна `yumiwatch:playback` сообщают одинаковый объект:

```ts
{
  version: 1,
  reason: 'timeupdate', // также sourcechange, playing, pause, seeking, seeked,
                        // buffering, ended, skip, dispose, saved, saveerror
  timestamp: Date.now(),
  playback: {
    animeId, videoId, episode, playerId, provider, dubbing,
    sourceHost, quality, format, relay,
    position, duration, watchedSeconds, playing, sync
  },
  // Только у reason: 'skip':
  skip: { kind: 'opening', from: 15, to: 105, automatic: true }
}
```

`timeupdate` публикуется не чаще раза в секунду; перемотки и пропуски не увеличивают `watchedSeconds`. `sync: 'saved'` появляется после подтверждения API (для гостя — после локальной записи). События не содержат токен аккаунта, полный подписанный URL видео или ключи relay. Callback пока относится к нашему плееру; iframe использует существующие протоколы источников.

Метки опенинга/титров берутся у фактически воспроизводимого варианта Yummy и уточняются метаданными источника: Kodik `parseSkipButton`, Alloha `skipTime`, Aksor `opening_start/length`, `ending_start/length`. Дополнительно читаются именованные главы/метаданные видео и HLS `EXT-X-DATERANGE` из уже загруженных движком манифестов. Неподдерживаемые или отсутствующие метки не заменяются приблизительными интервалами.

В самом видео есть кнопка ручного пропуска. Автопропуск опенинга и титров включается отдельно, по умолчанию выключен и сохраняется на устройстве. Он работает во время воспроизведения один раз на интервал; возврат перемоткой не создаёт цикл пропусков. Титры пропускаются до конца указанного интервала, сохраняя сцену после них. В браузерах с нативным полноэкранным видео доступность HTML-кнопки пропуска зависит от браузера; автопропуск продолжает работать по событиям видео.

Кнопка продолжения в карточке аниме объединяет общую историю аккаунта, `watched` у серий из `/anime/{id}/videos` и локальные точки восстановления по дате. Поэтому продолжение работает и для тайтлов вне первой страницы общей истории. При объединении источников одной озвучки сохраняется вариант серии с самым свежим серверным просмотром. Панель серий нашего плеера показывает серверный прогресс и текущие локальные точки просмотра.

Плеер передаёт кандидатов одной серии и озвучки команде Tauri `resolve_candidates`. Отдельный процесс или адрес сервера не требуется; настройка HTTP-resolver удалена.

IPC возвращает `provider`, `videoId`, `duration`, `streams: [{ quality, type, url, fallback? }]`. Логин, пароль и токены Yummy в обработку потоков не передаются. Rust допускает только HTTPS-домены известных плееров, запрещает редиректы, ограничивает размер ответов и время запроса. Для Alloha и CVH клиент получает идентификаторы зарегистрированных ресурсов внутреннего протокола `yumiwatch-media`, для Kodik/Aksor — прямые ссылки. Метаданные кэшируются в памяти на 30 секунд, максимум 64 записи.

Кандидаты разбираются параллельно с запаздыванием 300 мс по индексу. Быстрый резерв ждёт preferred-кандидата до двух секунд; ошибка preferred освобождает готовый резерв сразу, а зависание не блокирует его после priority window. Сессии Alloha и ресурсы CVH регистрируются только для выбранного результата: проигравшие и отменённые attempts не занимают общий лимит и не могут вытеснить активный поток.

Меню качества объединяет и сортирует разрешения всех доступных источников текущей серии и озвучки. Команда `inspect_stream_qualities` собирает метаданные без загрузки видео и использует тот же кэш кандидатов, что и `resolve_candidates`. В режиме источника «Авто» плеер сначала ищет точное разрешение. Если оно недоступно, плеер подбирает резервное качество. При ручном выборе плеер берёт ближайшее качество ниже в том же потоке. Если ниже ничего нет, меню позволяет выбрать другое качество или источник. При смене потока сохраняются позиция, пауза, громкость и скорость.

- Kodik: публичная HTML-страница → параметры `vInfo` и подписи → POST `/ftor` → декодирование `links`. Для адресов `*.mp4:hls:manifest.m3u8` вместе с HLS возвращается `fallback: { type: "mp4", url }`. При автоматическом выборе Kodik MP4 идёт последним среди источников подходящего качества. После сбоя HLS плеер сначала проверяет другие источники серии. Вручную для Kodik можно указать HLS или MP4. Рекламные поля `vast`, `reserve_vast`, `advert_script` не передаются клиенту и не исполняются.
- Aksor: публичный `/api/video/{id}` → доступные MPD/HLS-потоки. Если источник содержит только 1080p, более низкое качество не выдумывается.
- CVH: Rust обращается к API playlist/video и регистрирует медиа во внутреннем протоколе WebView. Озвучка и номер серии должны совпасть; соседняя серия или другая озвучка автоматически не подставляются. Субтитры отделены от озвучки. В браузерном предпросмотре сохранён прямой доступ к API с CORS.
- Alloha: HTML с Referer YummyAnime → разбор `fileList` и nonce → POST `/bnsi/movies/{id}`. Текущий служебный заголовок берётся из публичного app-бандла; этот код не исполняется. Рекламные SDK не загружаются. CDN отклоняет чужой Origin, поэтому HLS-плейлисты и сегменты идут через внутренний протокол WebView. Ссылки на CDN и служебные токены остаются в Rust, клиент получает случайные идентификаторы ресурсов. Разрешён только проверенный CDN `*.userplay.live` и каталоги текущей серии, редиректы запрещены. До 8 сессий, срок до 45 минут, простой до 3 минут; Range поддерживается; размер и число одновременных запросов ограничены. Для варианта «Субтитры» выбирается исходная японская дорожка и полный русский VTT по умолчанию; дорожка включается в нативном видео или Shaka. Это экспериментальный адаптер к недокументированному протоколу.

MP4 проигрывается нативным `<video>`; HLS/DASH — лениво загружаемым Shaka Player, на Safari и устройствах без MediaSource используется нативный HLS, когда доступен. Chromium с ответом `canPlayType = maybe` использует Shaka: нативная ветка может выдать ошибку разбора после сбоя сегмента. Восстанавливаемые ошибки Shaka не отбрасывают источник; остановленный VOD-загрузчик получает до двух явных сетевых повторов до смены источника, с общим контролем отсутствия кадров. `emptied`/`abort` сами по себе не считаются окончательной ошибкой. Готовность восстанавливается и по `loadeddata`/`playing`, если событие metadata уже прошло. Shaka не скачивается при установке PWA: его собственный файл кэшируется при первом использовании. Рекламные SDK в наш плеер не подключаются. Время сохраняется каждые 10 секунд, при паузе, смене режима и уходе из просмотра. При смене качества с отдельным URL новый поток заранее загружается во второй, беззвучный video-слой. Текущий слой продолжает играть до загрузки и декодирования кадра замены на той же позиции. После переключения старый декодер освобождается. Сохраняются пауза, громкость, выключение звука, скорость, меню и полный экран. Ошибка или 20-секундный таймаут подготовки оставляет текущее качество; отменённый выбор не может примениться позже. Для дорожек одного адаптивного манифеста Shaka переключает вариант без очистки уже загруженного буфера. Подписанные адреса потоков и сессии Alloha остаются в памяти и не сохраняются в публичный API-кэш.

`npm run check:player` (алиас `check:player-ui`) проверяет настоящий VideoSurface с Rust-обработкой потоков, декодированием кадров, перемоткой и сменой качества. `npm run check:app` проверяет собранный интерфейс, панели, навигацию и восстановление просмотра. Обе проверки используют Rust `media_probe` через stdin/stdout без веб-сервера; для живых источников нужен доступ в сеть. Они запускаются отдельно от unit-тестов.

Rust и WebView работают на одном устройстве; служебные заголовки и подписанные ссылки остаются в памяти приложения. Внешний или локальный HTTP-resolver не используется.

Rust загружает медиа Alloha и CVH без перекодирования и записи на диск, затем передаёт данные libmpv или WebView. Удалённый relay не требуется. Лицензия Shaka сохранена в `public/licenses/shaka-player.txt`.

### Проверка Alloha без relay — 14 ноября 2026

Повторно проверены master/variant HLS-плейлисты, init MP4 и видеосегмент одной публичной серии. Контрольные запросы с текущими служебными заголовками и Origin `https://alloha.yani.tv` получили HTTP 206. С Origin нашего GitHub Pages (`https://vicimpa.github.io`), localhost, другого HTTPS-сайта, YummyAnime, а также без Origin и с `Origin: null` все четыре типа ресурсов получили HTTP 403. Перенос служебных значений в URL-параметры `t`/`b` не помог.

В изолированном headless Chrome запрос с origin приложения и запрос из sandbox с непрозрачным origin также вернули HTTP 403 при доступном CORS (`Response.type === "cors"`). Контроль из origin Alloha вернул 206. Это ограничение доступа на CDN: одно проксирование плейлиста оставляет видеосегменты недоступными. Работа прямого нативного video с URL-параметрами не подтвердилась.

Для текущего проверенного потока не найден рабочий способ оставить собственный плеер обычной PWA и убрать передачу сегментов через relay. Браузер управляет заголовком Origin, включая запросы service worker. Изменения протокола поставщика могут потребовать повторной проверки. Клиент сначала пробует CVH, затем Kodik и Aksor, а Alloha используется как резерв при получении ссылки; ошибка видео или 20 секунд загрузки без кадров запускает перебор оставшихся источников той же серии и озвучки. Неудачные videoId исключаются до явного повтора либо смены серии/озвучки; при потере сети источники не исключаются. Позиция, состояние паузы, звук и скорость переносятся в новый поток. После исчерпания источников остаются повторная загрузка и возврат к аниме, включая полный экран.

### Service worker и публичные CORS-прокси — 15 ноября 2026

На одноразовом локальном origin и в отдельном headless Chrome зарегистрирован настоящий service worker с обработчиком fetch. Он попробовал получить свежий публичный сегмент Alloha, задав Origin плеера. Режим cors вернул HTTP 403; no-cors дал непрозрачный ответ со статусом 0 и нулевым доступным телом, тогда как на сетевом уровне также был 403. Service worker остаётся в модели безопасности браузера и не заменяет нативный HTTP-клиент. Правила [Origin](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_request_header) и [respondWith](https://developer.mozilla.org/en-US/docs/Web/API/FetchEvent/respondWith) не позволяют превратить такой ответ в читаемые видеобайты.

Короткий запрос свежего публичного HLS-плейлиста через cors.lol вернул 429; AllOrigins не ответил за 12 секунд. Это результаты отдельных запросов, а не доказательство постоянной недоступности сервисов. В [публичном коде cors.lol](https://github.com/BradPerbs/cors.lol/blob/main/main.go) upstream-запрос всегда GET, Origin не задаётся, лимит — 20 запросов за 5 минут. [AllOrigins](https://github.com/gnuns/allOrigins/blob/master/app/http-client.js) не предоставляет нужной настройки Origin через публичный API. Пользовательские пароли и токены Yummy в проверках не передавались.

Возможна схема «PWA → service worker/сетевой адаптер → управляемый CORS proxy → Alloha», где внешний сервис меняет upstream Origin и передаёт все видеосегменты, а клиент переписывает HLS-адреса. Для полного отказа от нашего backend необходимо также перенести получение метаданных в клиент и проксировать POST bnsi. Эта схема ещё не реализована и не проверена на Alloha с управляемым сервисом.

У [corsproxy.io](https://corsproxy.io/pricing/) свободный тариф ограничен 10 000 запросами и 1 ГБ в месяц, новые production-домены требуют платный план согласно актуальному FAQ. Передача всех типов файлов и изменение upstream-заголовков указаны для Production ($29/месяц). На странице pricing также предлагается бесплатное спонсирование open-source и образовательных проектов. Одобрение, включённые функции и применимость к HLS/Alloha требуют отдельного подтверждения сервиса; это не автоматически доступный бесплатный видеопрокси.

Дополнительно проверен [Corsfix](https://corsfix.com/docs/cors-proxy/header-override), который документирует подмену Origin через `x-corsfix-headers`. Контрольный запрос к example.com с localhost прошёл (200). Запрос текущего длинного Alloha master URL с той же настройкой получил HTTP 431 от сервера прокси; браузерный fetch завершился сетевой ошибкой, поскольку ответ не содержал CORS-заголовков. Это ограничение конкретной проверки, а не доказательство отказа всех реализаций прокси. [Бесплатный план Corsfix](https://corsfix.com/pricing) заявляет 100 МБ трафика и одного одновременного пользователя, что само по себе мало для видеопросмотра.

### Завершение и автоматические действия

Конец определяется по `ended` и фактической позиции у длительности. Пропуск титров до конца переводит видео в завершённое состояние сразу, не ожидая, что движок пришлёт `ended` после seek. В нём нет буферизации или таймаута источника; сохранённый intent воспроизведения выключен. Включение автоследующей серии уже после завершения сразу показывает отсчёт, без нового seek. Повторные `ended` не создают второй переход. Перемотка назад открывает новый цикл завершения; сцены после метки титров не пропускаются.

`AutoActionCountdown` даёт пять секунд на отмену автопропуска опенинга, титров и автоследующей серии, либо кнопку «Сейчас». Пауза/перемотка убирает текущий автоматический пропуск; ручной пропуск остаётся мгновенным. Отмена действует для текущей метки/завершения, а при повторном включении автоследующей серии отсчёт можно запустить заново. В открытой боковой панели таймер переносится внутрь неё, сохраняя фокус и кнопки доступными.

Для Kodik и Alloha HLS включены `manifest.hls.sequenceMode: false` и `ignoreManifestTimestampsInSegmentsMode: true`. Их округлённые длительности `EXTINF` могут расходиться с непрерывными временными метками TS; прежнее выравнивание каждого сегмента создавало разрывы буфера, которые gap-jumping перескакивал. На 10-й серии 22919 с дублированной озвучкой после опенинга за 35 секунд до изменения было 9 скачков на 1–4 секунды, после — 0 в отдельных прогонах на 360p и 720p; пропущенных видеокадров не было в обоих случаях. Настройка применяется к Kodik и Alloha, штатная обработка настоящих разрывов не отключается. Для Kodik и Alloha также задан `streaming.inaccurateManifestTolerance: 2`: при восстановлении позиции и перемотке загружается предыдущий сегмент, если округление плейлиста ставит точку раньше фактического начала выбранного сегмента. Это требуется в WebKit, где Shaka по умолчанию выставляет нулевой допуск.

Для всех эпизодов задан `manifest.availabilityWindowOverride: Infinity`. Если источник не ставит `#EXT-X-ENDLIST` и Shaka принимает запись за live-плейлист, начало разрешённого диапазона перемотки не сдвигается вперёд при обновлениях: вся серия остаётся доступной для возврата.

## События YummyAnime, уведомления и сообщения

`src/core/YummyRealtime.ts` поддерживает одно WebSocket-соединение на окно приложения с `wss://socket{1,2,3}.yani.tv/socket`; если основной кластер недоступен, перебираются `wss://socket{1,2,3}.yummyani.me/socket`. Адреса резервного кластера взяты из публичного клиента `old.yummyani.me`; они независимы от выбранного REST-зеркала, сокеты не открываются на `old` или `ru` напрямую. Оба кластера явно разрешены в CSP Tauri. Протокол найден 17 ноября 2026 года в публичном worker сайта YummyAnime: JSON, `subscribe-events`, `subscribe-global` / `unsubscribe-global`, `update-user`, `update-profile`, `notification`, `new-message`, `message-edited`, `message-deleted`, `message-read`. Это протокол клиента сайта, а не опубликованный в Swagger контракт; его изменения могут потребовать адаптации. Анонимное подключение и `ping`/`pong` ранее проверены на трёх основных узлах; при повторной проверке 17 ноября 2026 года основной и резервный кластеры отвечали Cloudflare HTTP 530 / 1033, тогда как REST-зеркала `old` и `ru` отвечали HTTP 200. Доступность узлов зависит от сервиса. Личные события проверяются на синтетическом аккаунте, без доступа к реальной переписке.

Подтверждённый пользовательский токен передаётся в query подключения, как на исходном сайте. Адрес сокета и токен не логируются и не сохраняются в кэш. Гостям доступны только подписки на публичные объекты. При смене токена или выходе закрывается прежний сокет, отменяются HTTP-запросы, очищаются личные события и счётчики. Объектные подписки имеют общий счётчик потребителей и восстанавливаются после подключения. Heartbeat отправляется раз в 30 секунд; отсутствие `pong` 10 секунд приводит к повторному подключению. Повторы используют шесть узлов и экспоненциальную задержку с jitter до 30 секунд; код 1008 требует явного повтора или обновления сессии.

`src/lib/social.ts` загружает исходное состояние и восстанавливает его после обрыва. При недоступном сокете обновляет уведомления и список диалогов через REST раз в минуту; открытая переписка обновляется раз в 15 секунд, только при видимом окне и наличии сети. Повторная загрузка не накладывается на незавершённую, сохраняет позицию чтения и прекращается при выходе с экрана. Статус соединения объясняет, что обновления приходят с задержкой. События дедуплицируются, счётчики сверяются после серии событий. Собственное присутствие обновляется через `POST /profile/online` при видимом приложении не чаще раза в четыре минуты. Для поля `hash` используется случайный идентификатор установки, а не идентификатор аналитики. Подписки `user` обновляют статусы друзей; первоначальное подключение не порождает массовые уведомления об онлайне.

`#/notifications` показывает историю, категории, непрочитанные события и отметку прочтения через `POST /profile/notifications/{id}/read` или `/profile/notifications/read`. `#/messages?user={id}` загружает личный диалог, старые сообщения и отправляет текст только по нажатию «Отправить» через `POST /dialogs/{id}/messages`. HTML из уведомлений и сообщений отображается текстом; ссылки разрешены только на HTTPS-домены Yummy, известные страницы открываются внутри приложения. Уведомления хранятся в памяти; переписка сохраняется в отдельном кэше аккаунта.

Подписка на новые серии привязана к паре озвучка/плеер: исходное состояние берётся из `/users/{id}/lists/subs`, изменения — `PUT/DELETE /video/{id}/subscribe`. Кнопки находятся рядом с оригинальными плеерами на странице аниме. Настройки всплывающих событий и онлайна друзей сохраняются локально. Системные уведомления выключены по умолчанию; разрешение запрашивается только по действию пользователя. На Tauri используется официальный `tauri-plugin-notification`, в браузере — Notifications API. Закрытое приложение не получает push. Комнаты совместного просмотра этот протокол не реализует.

Проверки: `npm test`, `npm run build:web`, `cargo test --manifest-path src-tauri/Cargo.toml`, `npm run check:social`, `npm run check:controls`. Браузерные проверки запускают Chrome и WebKit с синтетическими REST/WebSocket peers: доставка без дублей, чтение уведомлений, отправка/получение сообщений, живой статус друга, подписка на серию, мобильная геометрия, кэш профилей и история переходов. Проверка controls использует настоящее управление плеера и фокус браузера с детерминированным media element, без сети. Скриншоты сохраняются в `/private/tmp/yumiwatch-social-qa`.

Экран сообщений занимает доступную высоту окна: список диалогов и переписка прокручиваются независимо, заголовок и поле ввода закреплены. Enter отправляет сообщение, Shift+Enter добавляет строку. При чтении старых сообщений новая доставка не сбивает прокрутку; доступна кнопка перехода к новым сообщениям.

Комментарии раскрывают ответы деревом внутри текущего обсуждения, без дополнительных панелей. `CommentThread` загружает ветки по запросу и сохраняет открытые ветки после публикации ответа. Одна нижняя форма используется для нового комментария и ответа выбранному автору; её компонент `src/ui/ChatComposer.tsx` общий с личными сообщениями. Поле растёт до 160 px, Enter отправляет текст, Shift+Enter добавляет строку, подтверждение IME не отправляет форму. Кнопки спойлера и отмены ответа не вызывают отправку. Черновик с адресатом сохраняется в sessionStorage отдельно для аккаунта и аниме, очищается после успешной публикации или выхода. Список прокручивается отдельно от формы, мобильная форма учитывает visual viewport клавиатуры.

`npm run check:comments` проверяет дерево, единственную форму, спойлеры без POST, закрепление ввода при прокрутке, уменьшение visual viewport и публикацию ответа в Chromium/WebKit при ширинах 1280, 390 и 320 px. Проверка использует синтетический API; реальные комментарии не публикуются. Снимки сохраняются в `/tmp/yumiwatch-comments-qa`.

Отметка прочтения (`POST /dialogs/{id}/messages/read`) возвращает `{ok:true}`, если состояние изменилось, и `{ok:false}` при повторной отметке уже прочитанного диалога (проверено на живом API 17 ноября 2026 года). На `{ok:false}` клиент подтверждает нулевой `unread_count` через `GET /dialogs?need_uid={id}`; ненулевой или неизвестный счётчик остаётся ошибкой. Уже прочитанные сообщения не вызывают повторную запись при открытии/фокусе. После подтверждения флаги входящих сообщений обновляются в состоянии и кэше.

`src/lib/chat-cache.ts` сохраняет до 200 диалогов и до 300 последних сообщений на собеседника в существующем ограниченном кэше IndexedDB (localStorage fallback). Кэш доступен только для подтверждённого текущего аккаунта, содержит только разрешённые поля сообщений, черновик и позицию чтения без токенов. При открытии сохранённая переписка показывается синхронно и обновляется в фоне; сетевой сбой её не скрывает. Socket edits/deletes/read receipts обновляют закрытые диалоги; текст удалённого сообщения очищается. Лишние сообщения подгружаются обычной пагинацией. Позиция устанавливается в layout effect до первого кадра, без timeout-прокрутки; при чтении старых сообщений сохраняется видимое сообщение и его смещение. Холодная загрузка показывает спокойный текстовый статус вместо заглушек карточек аниме.

`src/lib/profile-cache.ts` сохраняет только поля профиля, списки, друзей и статистику в существующий ограниченный кэш IndexedDB с localStorage fallback. Сохранённые данные доступны синхронно через `peek`, обновляются в фоне, разделены по аккаунтам и гостю. 401/403/404 удаляют соответствующую запись; сетевые сбои сохраняют последнюю версию. Сырой `/profile`, токены и содержимое переписки в этот кэш не попадают.

`PersonalRating` на странице аниме сохраняет оценку 1–10 через `PUT /anime/{id}/rate` с `{rate}`, снимает через `DELETE` и принимает только подтверждённый ответ `{rating,votes}`. Детали аниме с `user.rating` запрашиваются с токеном аккаунта и кэшируются отдельно от публичных данных. После сохранения обновляются копии в коллекции, личная статистика и распределение оценок; запоздалые ответы прежнего аккаунта не меняют текущий. Гостевые оценки хранятся в `Library.rated` локально. Подборка `#/profile?tab=collection&list=rated&sort=user_rating` включает оценённые тайтлы без статуса списка и сортирует по личной оценке, при равенстве — по названию. Сортировка `user_rating` доступна и для всей коллекции, неоценённые аниме идут в конце. В чужом профиле используется оценка владельца списка.

`npm run check:ratings` проверяет выставление, изменение, снятие оценки, повторную попытку после отказа API, личный топ и раскладку на 1280/390/320 px в Chromium/WebKit с синтетическим аккаунтом, без записей в YummyAnime. Снимки сохраняются в `/tmp/yumiwatch-personal-ratings-qa`.

`src/lib/navigation.ts` помечает собственные записи History API и сохраняет индекс в sessionStorage, поддерживая кнопки «Назад»/«Вперёд», Alt+стрелки и Cmd+скобки. Возврат из аниме восстанавливает исходный маршрут профиля с вкладкой и списком, а `page-scroll` — прокрутку. Переходы используют fade и короткое смещение 18–24px вместо проезда на весь экран; reduced motion и настройка анимаций сохраняются. `text-selection.ts` блокирует выделение всего окна и сохраняет обычный Select All в полях ввода. Pointer-фокус кнопок плеера не удерживает управление; открытые настройки и клавиатурная навигация остаются доступны.

## Discord Rich Presence

`src/core/DiscordPresence.ts` формирует карточку просмотра и управляет её жизненным циклом. `src/hooks/useDiscordPresence.ts` связывает её с обоими режимами плеера; `src/lib/discord-presence.ts` хранит настройку и отправляет IPC-команду. Функция включена по умолчанию и доступна в десктопном приложении при наличии `VITE_DISCORD_APPLICATION_ID` в `.env.local`. В Actions ID передаётся из secret `DISCORD_APPLICATION_ID`.

`src-tauri/src/discord.rs` хранит последнее состояние, повторяет подключение через 15 секунд и очищает карточку после 45 секунд без обновлений от интерфейса. `discord/ipc.rs` реализует локальный Discord RPC через Unix socket или Windows named pipe: handshake, SET_ACTIVITY, ответы, PING/PONG, ограничения размера и таймауты. Отдельная авторизация и токен Discord не используются. Браузерная и мобильная версии статус не публикуют.

Для нативной полосы прогресса Discord передаются обе метки `timestamps.start` и `timestamps.end`. При перемотке и изменении скорости границы шкалы пересчитываются. На паузе, при буферизации и потере сети таймер отсутствует; после пяти минут без воспроизведения карточка скрывается. Завершение серии, выход из плеера и отключение настройки очищают активность. При выборе превью используется постер без кадров серии.

## Обновления приложения

Проверка новых версий (`useReleaseUpdate`, `releases.ts`, `updates.rs`) запускается через 1 секунду и раз в 5 минут, пока окно видно и сеть доступна. Native и web сохраняют ETag и последний релиз, отправляют `If-None-Match`, а на 304 оставляют прежние данные. При `Retry-After`, `X-Poll-Interval` и исчерпании `X-RateLimit-Remaining` учитывается серверная пауза; повторные 404 проверяются не чаще раза в час. Запросы не используют токен аккаунта YummyAnime или общий GitHub-токен. Для публичных запросов GitHub действует лимит по IP; ETag уменьшает передачу данных, но не гарантирует бесплатные запросы без авторизации.

## Форматирование

`npm run format` форматирует исходники, скрипты и тесты через Prettier, Rust — через rustfmt. `npm run format:check` проверяет формат без записи файлов. Пустые строки разделяют объявления функций и типов, а внутри функций — смысловые этапы; связанные переменные остаются вместе. Интерфейс, прикладная логика и подписки разделены по ответственности. CI проверяет формат до сборки.

### Состояние серверов и возврат к основному API

В «Настройки → Подключение» отображаются выбранный API, последние замеры `api.yani.tv`, `old.yummyani.me`, `ru.yummyani.me`, время обновления и локальное состояние WebSocket. Данные берутся из публичного `https://yummystatus.me/api/health?timeRange=3hour` — маршрута, который использует сам YummyStatus. Для текущего состояния берётся последний по времени bucket, а не итоговый health за три часа. Отсутствующие или неизвестные замеры не считаются исправными, замеры старше десяти минут помечаются устаревшими. Сбой мониторинга не влияет на выбор API и не удаляет предыдущие данные.

Карточка обновляется раз в минуту только при видимом приложении и наличии сети, поддерживает ручной повтор и ссылку на первоисточник. В Tauri данные запрашивает команда `yummy_server_status`: фиксированный HTTPS-маршрут, без аккаунтных токенов, тайм-аут 10 секунд, лимит ответа 512 КБ. Публичный монитор не отдаёт CORS-заголовки: Vite проксирует фиксированный маршрут для локального веб-предпросмотра; в статической веб-сборке при запрете CORS остаются выбранный адрес, статус сокета и ссылка на YummyStatus.

## Отклик переключателей каталога

`ChoiceTabs` подтверждает выбор локально через `flushSync` до обновления родительского URL и списка аниме. Нажатие остаётся обычным `click`: `pointerdown` не выполняет действия, а CSS `:active` показывает состояние прижатой кнопки. Повторный выбор того же значения не запускает обработчик ещё раз.

Компонент синхронизируется с подтверждённым значением, переходами назад и вперёд и скрытием сохранённого экрана. Данные и ошибки продолжает обрабатывать каталог; подсветка вкладки не ждёт ответа API. Глобальных перехватчиков кликов и подавления событий нет.
